# Member teams and league applications

Members sign in with the existing Discord account and open `/my-teams` from Account. They can create a team without a prior manager grant, search/link its EA club, edit its name, and apply to leagues that staff have explicitly opened. The creator manages their own team; this never changes the account's global role or grants League Suite access.

Owner/admin can create on behalf of any active signed-in member and reassign the manager later. Handoff changes the manager of the same durable team ID: league applications remain attached and the previous manager immediately loses access through this API. Existing live Team Hub assignments continue through the existing assignment tool; registering a new team does not silently take over an established season's team or hub.

Staff open/close registration for domestic League Suite leagues through the My teams staff controls. In an empty league's Teams section, Set up member team registration creates/reuses its shared registration board and opens the setup for that exact league. This works before fixtures exist. Current board open/expiry settings and registration windows are checked dynamically. National selection remains separate. Nothing is public-open by default. Applications require an EA club verified through the existing search provider, start pending, and need owner/admin approval. Refresh approved member teams in the creation hub brings accepted teams and their current managers into the scheduling draft; generated schedules remain protected.

Acceptance creates `member_team_hubs` in the same database transaction. A pending/rejected team has no hub. A second league acceptance keeps the same hub and playbook; reassignment preserves it while immediately revoking the previous manager's access. Hubs appear in My teams and the existing My team hubs chooser and use the existing tactical editor. Both owner and admin can inspect/edit these new accepted-team hubs. Existing season 2 hub permissions remain unchanged. A new hub starts with no registered players; player roster enrollment for these new teams is still a separate pre-season step. No existing live roster is copied or guessed.

`member_teams`, `member_team_leagues`, `member_team_applications`, `member_team_hubs` and `member_team_audit` live in the main website D1 database beside account identities. Tables/indexes are initialized idempotently by the authenticated endpoint; `migrations/20261113_member_teams.sql` records the same schema. EA club IDs and normalized team names are unique; one team can apply to multiple leagues. Pending applications can be withdrawn/rejected and resubmitted. A club cannot be replaced while an application is pending/approved. Regular accounts may create up to five teams; writes and search are rate limited. Generated fixtures, automatic collection, public roster assignments and historical results are not modified by registration.

Writes validate same-origin requests, active sessions, current account IDs and optimistic revisions. Every successful change records its actor and before/after values in an atomic audit transaction. Unique write markers prevent a concurrent handoff or application change from producing a misleading audit entry. No passwords, OAuth tokens or bot credentials are stored in these records.

The future Discord bot should call the same service operations with its verified Discord actor and the same durable team IDs. Bot authentication/commands are not enabled by this release; the website works independently.

Validation: `scripts/team-registration.test.mjs` exercises real SQLite SQL and signed-in session lookups for members/staff/blocked accounts, ownership and handoff, unchanged global roles, explicit league opening/windows, EA verification, duplicate prevention, staff approval, preserved saved fixtures/results, failed writes/concurrency/audits, account/origin guards and public shell/publication. Browser checks use an isolated in-memory local database, never fake live teams.
